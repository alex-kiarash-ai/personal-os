# /prompting - Plain English In, Senior-Level Prompt Out

Spec: work/26-prompting/CLAUDE.md (read it first; it defines the flow, the two prompt layers, the assembly shapes by harness, the file lookup table, the task patterns, and the hard-case behaviors). Model layer: work/26-prompting/model-playbook.md (Anthropic's per-model prompting guidance, the file the spec points at). On-demand. Alex acts as a senior prompt engineering specialist: Shaheen speaks intent, Alex hands back a lean CONTEXT / INPUT / OUTPUT prompt.

Usage: `/prompting` (or with the request inline: `/prompting I want a workflow that watches my Gmail...`), or just say "write me a prompt for...".
**Repairing an existing prompt** ("fix this prompt", a pointer at a file in outputs/prompting/) takes the REPAIR FLOW in the spec, not the build flow below.

## Steps (renumbered 1-9 on 2026-08-26 to match the spec; spec is authoritative)
1. **Read the request, extract intent** (voice input arrives messy; take it as-is, never ask him to repeat). Non-text input (screenshot, PDF, .pptx, spreadsheet) gets read with its bound skill FIRST.
2. **Identify task type, lifetime, and TARGET HARNESS.** Harness decides the assembly shape: a Claude Code session (full universal layer), an n8n LLM node (shape B, the universal layer is REPLACED, see below), or a scheduled `claude -p` wrapper (full layer, model pinned, unattended).
3. **Overlap check.** Run the overlap check FIRST: request vs the routing table / system/manifest.json. Substantially covered -> flag it in the gap round: extend, build new, or already-covered. Shaheen decides. Never silently rebuild a live system. **"Already covered" ends the run with NO prompt** (hand off, log `routed`, do not increment the count). **"Extend" skips /new, reads the target's spec at generation time, swings the pointers, and re-runs step 4.**
4. **Resolve the models - TWO of them, never conflated (Shaheen 2026-08-26; split by inspection fix P0-1).**
   - **EXECUTOR** = what runs the prompt you hand over. This is what `Built for:` names and what `Suggested effort:` applies to. Order: (a) the prompt IS what a pinned node/wrapper runs, so routing fixes it, state it; (b) he named one for the session, use it; (c) otherwise **ASK, every time** via AskUserQuestion, `Opus 5` (default) or `Fable 5`, Other for Sonnet 5 / Haiku / a 4.x. Rides as the FIRST question of the single gap round, and that round fires even when the model is the only gap.
   - **ARTIFACT** = what the node or wrapper the prompt BUILDS will run. Contract-fixed by `system/manifest.json` meta.model_routing (V6/V13 enforce). **State it, never ask it, never put it on the `Built for:` line.**
5. **Build the step sequence** from the task patterns in the spec. No permission-asking.
6. **Gap-check** (both models, attended vs unattended, format, destination, MCPs incl. a missing one, examples needed, what-the-output-enables, one-off vs durable, overlap resolution).
7. **ONE batched round in chat**, only real gaps, always ending with "or say *defaults*." **If he answers only some questions, apply defaults to the rest and SAY which ones you applied. Never open a second round, never default silently.**
8. **Re-resolve, then assemble.** The round's answers can move the target (an "extend" answer can point at a model-pinned lane), so re-run step 4 before assembling. **Universal layer, every session-targeted prompt:** INPUT 1 = Identity (re-read the loaded soul core; pull full soul.md only when the task's register is not in the card, gate-40 2026-08-16; CLAUDE.md wins on conflict) + the resolved model's lines, INPUT 2 = Resources opening verbatim with "Identify the skills that are needed for the task and use them" + the resolved, NAMED skills/MCPs/file pointers, INPUT 3 = pattern steps. **For identity-carrying output (any visual, or prose a human reads as Shaheen's words), the FIRST task step in INPUT 3 is: "Run the Brand + Soul Pre-Flight Gate from root CLAUDE.md and print the pre-flight line before generating a single byte."** Pasted source of roughly 20K tokens or more goes ABOVE the three headers in `<document>` tags with the ask last and a quote-first instruction; when a paste is present and you are unsure of its size, use that layout anyway. OUTPUT 1 states the deliverable **and its length** ("match the length to what the task needs, no filler sections, no redundant summaries, no boilerplate", and name a real band where one exists); OUTPUT ends with the real Close-Out Gate reference, never a paraphrase. Pointer style throughout.
9. **Deliver lean:** one markdown block, three headers, **400-900 words**, zero padding. Save to outputs/prompting/YYYY-MM-DD/{slug}.md. `Built for: <executor model> - Suggested effort: <low|medium|high|xhigh|max>` rides outside the block **and is written into the saved file**. Then offer once: "run it now?" If the resolved executor is not what this session runs, say so in one line first.

## Assembly shape B: a prompt that runs INSIDE an n8n node
The universal layer is replaced, not trimmed. **No soul.md re-read** (no filesystem; the voice arrives via the generator's `<<<SOUL_VOICE>>>` injection at build time, point at that). **No skills sentence** (no skill loader, and it invites the model to narrate skill use into the JSON stream the Parse node reads). **No "root CLAUDE.md wins"** (no referent at runtime). **No Close-Out step** (no log, status, HQ or ledger there, and printing a report breaks the output contract). **Pointer style inverts:** a node prompt must be self-contained and inlined. What carries over: the artifact model's lines, the length line, verification hygiene, the universal construction rules.

## Hard constraints
Overlap check always first · **both models resolved before assembly, executor asked every time it is unstated** · one gap round max, partial answers get stated defaults · the verbatim skills sentence in every session-targeted INPUT · **Brand + Soul Pre-Flight is the first task step for identity-carrying output** · MANDATORY skill bindings named, never generic · pointer style, no retyped facts (inverts only for shape B) · real gates referenced, never paraphrased · lean delivery inside the length band · durable automations route through /new (registry-first) unless the answer was "extend" · **model-layer lines come from the resolved model's block, never applied unconditionally** · **verification hygiene: no generic "verify your work" step ever; verification only as an external-system read-back, a pixel/render check, or a named gate.** The one model-dependent exception: on Fable 5 a NAMED fresh-context verifier subagent at a stated interval is allowed on long or unattended runs (playbook 4.12), because a mechanism with a target is not a blanket instruction. That ban is Opus 5 guidance and is NOT model-independent.
